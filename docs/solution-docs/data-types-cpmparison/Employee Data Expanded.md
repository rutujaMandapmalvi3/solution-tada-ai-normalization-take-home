# Employee Canonical Mapping Proposal

Proposal only: no canonical models or mapper code have been changed. This is a review aid, not an approved implementation contract.

## Read this first

- The visible label Employee ID proposes the Python field employee_id, matching the current naming direction. It means the selected source employee identifier (previously called source_employee_id), not a newly generated global ID.
- Populate provider from adapter identity: prismhr, isolved, or ukg-ready. Preserve available client/legal/EIN scope; provider plus employee_id is not asserted to be globally unique across every tenant.
- Employee Number remains separate. UKG employee_id is preserved as ukg_employee_id, not used as the retrieval identifier.
- Preserve nulls where accepted; do not fabricate missing fields, defaults, enum meanings, units, or IDs.
- A provider prefix in a proposed destination denotes separate ownership. It does not require that exact nested JSON layout; final placement of provider-specific fields and metadata remains a design decision.
- Source array markers [] retain record boundaries. Repeated endpoint views are not separate canonical fields to merge automatically; provider-specific precedence and deduplication remain pending.
- Descriptions and verified source references are in [Employee Data Expanded](Employee%20Data%20Expanded.md). This proposal uses that inventory's current source types.
- Existing requiredness policy applies to source validation. Canonical requiredness and class layout are not changed by this document.

## Mapping actions

| Action | Meaning |
|---|---|
| Direct | Copy/rename an accepted shared meaning; retain the value. |
| Convert | A helper is proposed for representation changes. It is not implemented or approved merely by appearing here. |
| Preserve separately | Keep the source information without claiming equivalence to another provider's field. |
| Needs decision | Do not populate the proposed shared destination until the review question is resolved; preserve the source value meanwhile. |

## Decisions to review in batches

| Batch | Proposed direction | Decision needed |
|---|---|---|

| Pronouns | Keep all source pronoun values until precedence is agreed. | Choose one preferred source, conflict diagnostics, or retain both. |
| Gender/reporting | Separate ordinary gender, EEO override, and PrismHR designation. | Choose canonical concepts and verified code dictionaries. |

| Employment status/type | Keep source codes/IDs until dictionaries are verified. | Approve cross-provider meanings; do not equate class, status, and lookup IDs. |

| Other semantic matches | Preserve ambiguous identifiers/flags and address components separately. | Resolve citizenship, I-9, disability, union, job/code, legal scope, and region/postal differences in batches. |
| Unknown/extra fields and metadata | Retain outside shared business fields. | Choose final preservation/diagnostics placement; extras remain untyped unless explicitly modeled. |

## Specific proposals already discussed

- Preferred name: PrismHR preferredName + isolved nameAddress.preferredName.
- Nickname: PrismHR person.nickname + UKG nickname; no automatic preferred-name fallback.
- Salutation/prefix and suffix: preserve the user-approved correspondences.
- isolved uniqueId -> isolved_derived_employee_unique_id; UKG external_id -> ukg_external_id.
- UKG primary_account_id -> ukg_primary_account_id; optional and documented only for multi-EIN companies.
- UKG username -> ukg_username; PrismHR person.userId -> prismhr_portal_user_id.
- PrismHR person.hispanic -> is_hispanic, independent of ethnicity code/description.
- isolved eeoGenderOverride -> isolved_eeo_gender_override; this is a reporting override, not ordinary gender.
- Birth date proposes a helper producing YYYY-MM-DD. No timestamp is converted until timezone/truncation policy is approved.
- For marital status, candidate labels are single, married, divorced, widowed, civil_union, other, unknown. These are a proposal, not an inferred isolved enum.

## Documented lookup boundaries

- PrismHR supplied lookup-reference.json has no ethnic-code entries. OpenAPI GET /clientMaster/v1/getClientCodes documents options=Ethnic for client-specific codes.
- GET /codeFiles/v1/getEeoCodes with eeoCodeType=Ethnic concerns EEO setup codes. Do not assume that dictionary substitutes for employee client ethnic codes.
- isolved ethnicOrigin is documented only as an Ethnic Origin description; categories and equivalence are not established.
- PrismHR maritalStatus meanings are documented. isolved's description says only Marital status code; no cross-provider enum translation is assumed.
- UKG standard_work_day is milliseconds. It is not directly equivalent to standard/normal hours per pay period.
- PrismHR firstName's description conflicts with the field name. Its shared-name correspondence is based on the user's accepted review and remains a documentation gap.
